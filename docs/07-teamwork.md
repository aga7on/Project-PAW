## 3. Поток изменения

```
issue (что и зачем)
   ↓
ветка <зона>/<имя> от main
   ↓
работа + python tools/validate_mod.py
   ↓
PR (шаблон: что, зачем, как проверено, что не проверено)
   ↓
CI validate + ревью владельца зоны
   ↓
squash-merge в main
   ↓
ветка удалена, issue закрыт
```

Обходной путь только один: `hotfix/` для поломки, которая блокирует всех, с PR
задним числом в тот же день.

## 4. Горячие точки (где будут конфликты)

| Файл / место | Почему конфликт | Правило |
|---|---|---|
| `ProjectPAW/mod.info` | все хотят поднять версию | правит Артём, остальные не трогают |
| `workshop.txt` | описание, теги | правит Артём перед публикацией |
| `ProjectPAW/media/lua/shared/Sandbox/ProjectPAW.lua` | Артём выключает свет/машины, Андрей крутит баланс | файл у Андрея; Артём присылает значения через issue |
| `docs/00-index.md` | общая карта документов | Артём; новый документ — через PR с правкой индекса |
| `docs/data/**` | все хотят «поправить число» | только перегенерация скриптом |
| `ProjectPAW/media/scripts/ProjectPAW/items/*` | Влад может захотеть предмет для сюжета | предметы сюжета — в `items/` через PR Артёма, либо в зоне Влада как отдельный файл `pzm_story_items.txt` |
| `ProjectPAW/media/lua/server/ProjectPAW/` | события мира и удаление пересекаются по смыслу | серверная логика — Влад; удаление — только флаги и скрипты Артёма |

Если правка неизбежно задевает две зоны — два PR, второй после первого. Не «один большой,
чтобы не возиться».

## 5.1. Подключение нового участника

Порядок действий (нужен доступ администратора репозитория):

1. **Приглашение.** GitHub → Settings → Collaborators → *Add people* → ввести логин,
   роль **Write**. Приглашение придёт на почту или в GitHub-уведомления.
2. **Принятие.** Участник принимает приглашение: иначе он не сможет пушить ветки.
3. **`CODEOWNERS`.** Добавить логин в `.github/CODEOWNERS` в секцию своей зоны.
   GitHub начнёт автоматически запрашивать ревью у владельца зоны. Сейчас там уже
   `@vladvolt27-rgb` (Влад) и `@FruitPaw1337` (Андрей).
4. **Локальная настройка** (участник делает сам):

   ```powershell
   git clone https://github.com/aga7on/Project-PAW.git
   cd Project-PAW
   New-Item -ItemType Junction -Path "$env:USERPROFILE\Zomboid\mods\ProjectPAW" `
     -Target "$PWD\ProjectPAW"
   python tools/validate_mod.py
   ```

5. **Первая ветка.** `.\sync.ps1 branch vlad/first-task` (или `andrey/...`), работа,
   `.\sync.ps1 push "map: ..."`, затем PR.

Пока в репозитории один человек с правом записи, мерж PR требует второго аккаунта:
одобрить собственный PR нельзя. Это ожидаемое ограничение, а не баг настройки.

**Временный обход для администратора** (только пока нет второго участника; после мержа
защиту вернуть):

```powershell
# 1. разрешить администратору обойти защиту
gh api -X DELETE repos/aga7on/Project-PAW/branches/main/protection/enforce_admins

# 2. смержить свой PR (squash, с удалением ветки)
gh pr merge <номер> --squash --admin --delete-branch

# 3. вернуть строгую защиту
gh api -X POST repos/aga7on/Project-PAW/branches/main/protection/enforce_admins
```

После подключения второго участника обход не нужен: ревью ставит он.

## 6. Definition of Done

Задача считается сделанной, когда:

- [ ] Изменение в зоне автора, чужие файлы не тронуты
- [ ] `python tools/validate_mod.py` проходит
- [ ] PR описывает ручную проверку (или честно говорит, что её не было)
- [ ] Документы обновлены, если изменились факты или числа
- [ ] Ветка смержена squash-коммитом, issue закрыт
- [ ] Если менялись числа или правила — строка в журнале решений

## 7. Разделение дорожной карты

Из `06-roadmap.md`, по владельцам:

| Этап | Содержание | Владелец | Зависимость |
|---|---|---|---|
| 0 | Тест `Obsolete = true` в игре | Артём | блокирует этап 2 |
| 1 | Пресет песочницы | Андрей (числа) + Артём (флаги) | зависит от 0 |
| 2 | Удаление современного контента | Артём | этап 0 |
| 3 | Профессии, трейты, навыки | Андрей | этап 2 |
| 4 | Пороховое оружие | Артём (скрипты) + Андрей (баланс) | этап 2 |
| 5 | Быт без электричества | Андрей | этап 1 |
| 6 | Карта и мир | Влад | этапы 1–2 |
| 7 | Гужевой транспорт | Влад (решение), Артём (техника) | этап 6 |
| 8 | Луки и арбалеты | не назначен | после релиза |

Критический путь: **0 → 2 → 6**. Пока не проверен `Obsolete`, Артём не может двигаться,
а Влад не знает, что именно исчезнет из мира.

## 8. Коммуникация

- Один вопрос — один issue. «Обсудим в чате» заканчивается тем, что через неделю
  никто не помнит решение.
- В PR указывать `Closes #12`, чтобы задачи закрывались сами.
- Спор о числах решается тестом в игре, а не аргументом. Нет теста — нет решения.
- Раз в неделю: пройтись по открытым PR и issues, обновить журнал решений.
- Язык документации — русский; код, ID предметов и имена файлов — английский.

## 9. Чего в процессе нет

- **Нет релизных веток.** Релиз — тег на `main`.
- **Нет `develop`.** Три человека не тянут две долгоживущие ветки.
- **Нет обязательного code review двух людей.** Достаточно одного владельца зоны.
- **Нет автоматического форматирования всего репозитория.** Оно создаёт гигантские
  диффы и конфликты.
